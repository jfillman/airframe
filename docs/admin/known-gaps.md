# Airframe: known gaps

Found in use on 2026-09-26/27 while creating `baggage-api`. Each has evidence, so it can be picked up later.

| # | Gap | Evidence | Direction |
|---|---|---|---|
| 1 | **`configMapGenerator: true` on an `ApplicationEnvironment` adds a third ArgoCD source pointing at `<cluster>/<env>/configmap`, and nothing creates that folder.** The Application fails with `app path does not exist` until someone adds it. Tower's Config tab creates it only on the first config-file edit, which is too late. | `baggage-api-staging`; unblocked by adding `prod/staging/configmap/kustomization.yaml` (PR #5 in gitops-baggage-api). | The `ApplicationEnvironment` composition seeds `configmap/kustomization.yaml` (an empty generator named `<app>-app-config`, `disableNameSuffixHash: true`) when the flag is set, as a `RepositoryFile` with `overwriteOnCreate: false` and the same external-name adoption as `values.yaml`, so Tower's later edits are never overwritten. Test it through a copy of the composition. Not built. |
| 2 | **A brand-new Flight environment can fail its first sync and stay failed.** The PreSync `platform-outcome-presync` Job needs the `platform-outcome-hook` ServiceAccount, which lives in a separate identity Application; on a first sync the two race. The old comment claimed `selfHeal` retries; it does not retry a failed operation. | `baggage-api-staging`: `error looking up service account ... not found`, then `Job was active longer than specified deadline`. | **Resolved 2026-10-06 (glidepath ADR-0021 phase 3b): the PreSync/PostSync/SyncFail hook Jobs and the `airframe-identity` chart they needed are removed, so there is nothing left to race.** Was: **Fixed 2026-09-27:** `syncPolicy.retry` (5 tries, 30 s doubling, 10 min cap) in the tenant-onboarding ApplicationSet in apron and gitops-cluster-prod. Also consider ordering the two Applications. |
| 3 | **`releaseTracking.relayHostAliasIP` is written with the dev node's `status.hostIP`, which the prod cluster cannot route to.** `baggage-api` staging got the dev node's IP `<dev-node-ip>`; the value that works is the host's LAN IP `<host-lan-ip>`, which had been hand-fixed on flight-api and is overwritten by the next release. | `platform-outcome-syncfail` Job timing out. Source: Glidepath `open-release-pr.yaml` (`fieldRef: status.hostIP`). | **Resolved 2026-10-06 (glidepath ADR-0021 phase 3b): `relayHostAliasIP` and the hook Jobs that used it are gone.** Was: The parked fix: a per-cluster `relayHostAliasIP` in the cluster registry entry, with `hostIP` as the fallback. Every release re-breaks the hand fix until this lands. |
| 4 | **The Ground/Flight `rollout: null` bootstrap seed is now unnecessary** (the chart guard covers it) but is still written by the composition. | `values-yaml.yaml` in the `ApplicationEnvironment` composition. | Leave until the composition is next touched; a past change to it wiped a live file. |
| 5 | **Tower's Provisioning and Environment views list GitHub files from the XR's `resourceRefs` plus the live `RepositoryFile` MRs.** Since the scaffold ledger (airframe v0.3.131, review C4) a scaffold file leaves both once it is written, so those views show only the platform-owned files (Repository, `identity.yaml`, SecretStore XR requests) and no longer the boilerplate it scaffolded. | `tower/src/provisioning/useProvisioning.ts` (`GITHUB_KINDS`, `toManaged`), `tower/src/environments/useEnvLifecycle.ts`. | Tower reads `status.scaffold.done` on the application / `ApplicationEnvironment` XR and renders those names as done scaffold steps. Not built. |
| 6 | **A cluster rebuild re-composes every scaffold with the template's default filename.** The ledger lives in XR status, so a rebuilt cluster starts empty; the pinned external-name adopts the existing file for every scaffold whose name matches the template default. The six repos whose container file is `Dockerfile` (template default `Containerfile`) would get a second file created next to it, exactly as before the ledger (the live-state pin only protects an XR that still observes its own MR). | `src-repo.yaml` `scaffoldFile` helper in the four app stacks; the 2026-09-23 canary notes. | Record the pinned filename in the ledger (`status.scaffold.files[]` with `name`+`file`) and use it as the default on the next compose, or rename those six files to `Containerfile`. Unchanged by C4; noted so a rebuild is not a surprise. |
